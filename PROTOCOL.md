# mylocalon Tunnel Protocol — v1

Status: **Draft / MVP**
Protocol version: `1`
Transport: **WSS** (secure WebSocket) only

This document is the **normative contract** between a mylocalon client (CLI or any
language SDK) and the mylocalon Gateway. Any SDK that implements this document
works against the Gateway with **no Gateway changes**. The Gateway MUST NOT
require knowledge of any specific client language.

Key words **MUST**, **MUST NOT**, **SHOULD**, **MAY** are used per RFC 2119.

---

## 1. Design goals

1. **Language independence** — a JSON message set any language can produce/parse.
2. **Firewall friendliness** — the client always dials *out*; no inbound ports.
3. **One socket per tunnel** — control + data multiplexed by `type`.
4. **Stateless Gateway auth** — token is a signed JWT verified offline (see §4).
5. **Forward-compatible** — capabilities are negotiated, so v1.x can add features
   (e.g. binary body streaming) without breaking v1 clients.
6. **Correctness before efficiency** — v1 carries HTTP bodies as base64 in JSON.

---

## 2. Transport & connection

- Endpoint: `wss://gateway.mylocalon.com/tunnel`
- WebSocket subprotocol (`Sec-WebSocket-Protocol`): `mylocalon.v1`
  - The Gateway echoes the highest subprotocol it supports. If none match, it
    completes the WS upgrade only to send a `GOAWAY` (§9) then closes, OR rejects
    the upgrade with HTTP 426. Clients MUST handle both.
- All application messages are WebSocket **text** frames containing one JSON
  object. Binary frames are **reserved** for a future negotiated body mode (§12)
  and MUST NOT be sent in v1.
- One tunnel == one WSS connection. Multiple tunnels == multiple connections.

---

## 3. Message envelope

Every message is a single JSON object with at minimum a `type`:

```json
{ "type": "STRING", "...": "type-specific fields" }
```

- `type` — required, uppercase snake case, from the table in §5.
- `reqId` — present only on HTTP request/response messages; correlates a
  response to its request. Opaque string, unique per in-flight request on a
  given tunnel. Generated by the **Gateway**.
- Unknown fields MUST be ignored by receivers (forward compatibility).
- Unknown `type` values: the receiver SHOULD reply with `ERROR`
  `code=PROTOCOL_ERROR` and MAY close the connection.

Numbers are JSON numbers; timestamps are Unix milliseconds (integer). Binary
payloads (HTTP bodies) are **base64 (standard, padded)** strings.

---

## 4. Authentication (token exchange)

- The client obtains a **JWT** from the Platform (via `mylocalon login`). The
  Platform signs it with an **Ed25519 private key**.
- The Gateway holds only the **Ed25519 public key** and verifies the JWT
  **offline** — no call to the Platform on the hot path. The Gateway can never
  mint tokens.
- Required JWT claims:
  - `sub` — user id
  - `iss` — `mylocalon-platform`
  - `aud` — `mylocalon-gateway`
  - `exp`, `iat` — standard expiry / issued-at (short TTL recommended, e.g. ≤1h
    for CLI session tokens; long-lived API keys are exchanged for short JWTs by
    the Platform — the Gateway only ever sees short-lived JWTs)
  - `plan`, `limits` (optional) — e.g. `maxTunnels`, `maxBodyBytes`, allowed
    reserved subdomains. Authoritative limits still come from the Platform; these
    are hints the Gateway MAY enforce.
- **Revocation:** short TTL is the primary control. For immediate revocation the
  Gateway checks a Redis denylist keyed by JWT `jti` (optional in v1).

The token is sent in the `HELLO` message (§6.1), never logged, never placed in a
URL.

## 5. Message catalog

| `type`             | Direction        | Purpose                                        |
|--------------------|------------------|------------------------------------------------|
| `HELLO`            | client → gateway | Handshake: version, auth, tunnel request/resume |
| `WELCOME`          | gateway → client | Tunnel accepted: tunnelId, subdomain, url       |
| `PING`             | either           | Heartbeat request                               |
| `PONG`             | either           | Heartbeat reply                                 |
| `HTTP_REQUEST`     | gateway → client | Forward an inbound HTTP request                 |
| `HTTP_RESPONSE`    | client → gateway | Response from the local app                     |
| `ERROR`            | either           | Recoverable, per-message error                  |
| `GOAWAY`           | gateway → client | Gateway is closing this connection (with reason)|
| `CLOSE`            | client → gateway | Client is closing the tunnel intentionally      |
| *(reserved)* `WS_*`| either           | Raw WebSocket forwarding — **v1.x**, see §12     |

## 6. Handshake

### 6.1 `HELLO` (client → gateway) — first message after WS open

```json
{
  "type": "HELLO",
  "protocol": 1,
  "token": "<JWT>",
  "client": { "name": "mylocalon-cli", "version": "0.1.0", "os": "darwin" },
  "tunnel": {
    "subdomain": "myproject",      // optional: request a reserved subdomain
    "targetHint": "http://localhost:3000"  // informational only
  },
  "resume": {                       // optional: reconnect an existing tunnel
    "tunnelId": "tnl_abc123",
    "resumeToken": "rsm_..."
  }
}
```

- `protocol` MUST be `1`. If the Gateway does not support it → `GOAWAY`
  `code=VERSION_UNSUPPORTED`.
- Exactly one of a **fresh** request (`tunnel`) or a **resume** (`resume`) is the
  intent; if `resume` is present the Gateway attempts resume first (§10) and
  falls back to a fresh tunnel only if the client set `tunnel` too.
- If `tunnel.subdomain` is set, the Gateway asks the Platform-owned data (via its
  own read path) whether the `sub` user owns that reserved subdomain. Not owned →
  `GOAWAY` `code=SUBDOMAIN_FORBIDDEN`. Owned but currently active elsewhere →
  `SUBDOMAIN_TAKEN`. Absent → the Gateway generates a random subdomain.

### 6.2 `WELCOME` (gateway → client)

```json
{
  "type": "WELCOME",
  "tunnelId": "tnl_abc123",
  "subdomain": "abc123",
  "url": "https://abc123.mylocalon.com",
  "resumeToken": "rsm_9f...",       // used for reconnect within grace window
  "heartbeat": { "intervalMs": 15000, "timeoutMs": 45000 },
  "limits": { "maxBodyBytes": 10485760 }
}
```

Receiving `WELCOME` moves the client tunnel state to `ACTIVE` (§11). The client
MUST persist `tunnelId` + `resumeToken` in memory for reconnects.

---

## 7. Heartbeat

- After `WELCOME`, the party **initiating** heartbeats is the **Gateway**: it
  sends `PING` every `heartbeat.intervalMs`. The client MUST reply `PONG`
  promptly. The client MAY also send its own `PING` to detect a dead socket.

```json
{ "type": "PING", "ts": 1721800000000 }
{ "type": "PONG", "ts": 1721800000000 }
```

- If the Gateway receives no message (`PONG` or any other) within
  `heartbeat.timeoutMs`, it moves the tunnel to `DISCONNECTED` and starts the
  resume grace timer (§10). App-level PING/PONG is used (not just native WS
  frames) so every SDK can implement it uniformly.

---

## 8. HTTP forwarding

### 8.1 `HTTP_REQUEST` (gateway → client)

```json
{
  "type": "HTTP_REQUEST",
  "reqId": "rq_01H...",
  "method": "POST",
  "path": "/api/users?limit=10",     // path + raw query
  "headers": [["content-type","application/json"], ["accept","*/*"]],
  "bodyB64": "eyJuYW1lIjoiYSJ9",      // base64 of raw body, "" if none
  "bodyTruncated": false,
  "remoteIp": "203.0.113.9",          // original client IP (from Caddy)
  "receivedAt": 1721800000000
}
```

- `headers` is an **array of pairs** (not an object) to preserve duplicates and
  order (e.g. multiple `Set-Cookie`). Hop-by-hop headers (`Connection`,
  `Keep-Alive`, `Transfer-Encoding`, etc.) are stripped by the Gateway.
- If the request body exceeds `limits.maxBodyBytes`, the Gateway rejects it at
  the edge with HTTP 413 and does **not** forward — clients never see oversized
  bodies. `bodyTruncated` is reserved for the future streaming mode.

### 8.2 `HTTP_RESPONSE` (client → gateway)

```json
{
  "type": "HTTP_RESPONSE",
  "reqId": "rq_01H...",
  "status": 200,
  "headers": [["content-type","application/json"]],
  "bodyB64": "eyJvayI6dHJ1ZX0=",
  "durationMs": 12
}
```

- The client MUST echo the same `reqId`. The Gateway matches it to the waiting
  HTTP response writer. Unknown/expired `reqId` → the Gateway drops it (the
  public request already timed out).

### 8.3 Local app errors

If the client cannot reach the local target (connection refused, DNS, timeout),
it replies with an `ERROR` carrying the `reqId`:

```json
{ "type": "ERROR", "reqId": "rq_01H...", "code": "UPSTREAM_UNREACHABLE",
  "message": "dial tcp 127.0.0.1:3000: connection refused" }
```

The Gateway translates this into a public **502** (or **504** for
`UPSTREAM_TIMEOUT`) with a small mylocalon error page.

---

## 9. Errors & GOAWAY

### 9.1 `ERROR` — recoverable, does not necessarily close the socket

```json
{ "type": "ERROR", "reqId": "rq_...?", "code": "UPSTREAM_TIMEOUT",
  "message": "human readable", "retryable": true }
```

### 9.2 `GOAWAY` — the Gateway is terminating this connection

```json
{ "type": "GOAWAY", "code": "VERSION_UNSUPPORTED",
  "message": "protocol 1 required", "reconnect": false }
```

After sending `GOAWAY` the Gateway closes the WS. `reconnect: true` tells the
client it MAY reconnect (e.g. Gateway rolling restart); `false` means don't (e.g.
auth failure, revoked token).

### 9.3 Error codes

| `code`                 | Meaning                                          | Typical action        |
|------------------------|--------------------------------------------------|-----------------------|
| `VERSION_UNSUPPORTED`  | `protocol` not supported                         | GOAWAY, no reconnect  |
| `AUTH_FAILED`          | JWT invalid/expired/wrong aud                    | GOAWAY, re-login      |
| `AUTH_REVOKED`         | `jti` on denylist                                | GOAWAY, re-login      |
| `SUBDOMAIN_FORBIDDEN`  | User doesn't own requested reserved subdomain    | GOAWAY, no reconnect  |
| `SUBDOMAIN_TAKEN`      | Subdomain active on another tunnel               | GOAWAY, retry/other   |
| `TUNNEL_LIMIT`         | User exceeded concurrent-tunnel limit            | GOAWAY, no reconnect  |
| `RATE_LIMITED`         | Connection/request rate exceeded                 | backoff + reconnect   |
| `RESUME_EXPIRED`       | Resume grace window elapsed / unknown tunnelId   | fresh HELLO           |
| `PROTOCOL_ERROR`       | Malformed/unknown message                        | close, fix client     |
| `UPSTREAM_UNREACHABLE` | Client can't reach local app                     | public 502            |
| `UPSTREAM_TIMEOUT`     | Local app too slow                               | public 504            |
| `BODY_TOO_LARGE`       | Body exceeded `maxBodyBytes`                     | public 413            |

## 10. Reconnection & resume

Goal: a dropped socket should not change the public URL if the client returns
quickly.

1. On disconnect the Gateway keeps the tunnel record in Redis in state
   `DISCONNECTED` for a **grace window** (default 30s), holding the subdomain.
2. Client dials a new WSS connection and sends `HELLO` with
   `resume { tunnelId, resumeToken }`.
3. Gateway validates the `resumeToken` (hashed, stored in Redis) and that the
   grace window hasn't elapsed:
   - Valid → `WELCOME` with the **same** `tunnelId`/`subdomain`, state → `ACTIVE`.
   - Expired/unknown → `ERROR`/`GOAWAY` `code=RESUME_EXPIRED`; client retries with
     a fresh `HELLO` and accepts a new subdomain (unless it owns a reserved one).
4. In-flight requests during the gap are lost (public side already got 502/timeout);
   only the tunnel identity is preserved, not buffered traffic.

Clients SHOULD reconnect with jittered exponential backoff (e.g. 0.5s → 8s cap).

## 11. Tunnel state machine

Authoritative runtime state lives in **Redis** (Gateway). PostgreSQL (Platform)
keeps audit history only.

```
CREATED ──HELLO sent──▶ CONNECTING ──WELCOME──▶ ACTIVE
                                          │
                    socket drop / timeout │
                                          ▼
                                   DISCONNECTED ──resume ok──▶ ACTIVE
                                          │  │
                     grace expires / CLOSE│  └─reconnect attempt─▶ RECONNECTING ─▶ ACTIVE
                                          ▼
                                       CLOSED
```

| State          | Starts when                              | Set by  | Notify                    |
|----------------|------------------------------------------|---------|---------------------------|
| `CREATED`      | client instantiates tunnel object        | client  | local only                |
| `CONNECTING`   | WS dial begins / `HELLO` sent            | client  | local only                |
| `ACTIVE`       | `WELCOME` received                       | gateway | WELCOME msg + dashboard   |
| `DISCONNECTED` | heartbeat timeout / socket drop          | gateway | dashboard (grace running) |
| `RECONNECTING` | client begins a resume dial              | client  | local; dashboard on success|
| `CLOSED`       | explicit `CLOSE`/`GOAWAY` or grace expiry| either  | GOAWAY/close + dashboard  |

## 12. Reserved for v1.x (do not implement in v1)

- **Binary body mode** — negotiated in `HELLO` capabilities; streams request/
  response bodies as binary WS frames keyed by `reqId` for large/streaming payloads.
- **Raw WebSocket forwarding** (`WS_OPEN`/`WS_DATA`/`WS_CLOSE`) — tunnel the end
  user's WebSocket to the local app using stream ids over the same connection.
- **Capabilities negotiation** — `HELLO.capabilities: ["binaryBody","wsForward"]`,
  Gateway replies with the granted subset in `WELCOME.capabilities`. Absent ==
  v1 baseline. This is the forward-compat hook that keeps all of the above
  non-breaking.

---

## 13. Size & safety limits (enforced by Gateway)

| Limit                     | Default    | Notes                                  |
|---------------------------|------------|----------------------------------------|
| Max request body          | 10 MiB     | 413 at edge; overridable per plan      |
| Max response body (v1)    | 10 MiB     | buffered; streaming mode lifts this    |
| Max header bytes          | 32 KiB     | edge reject                            |
| Max WS message (control)  | 64 KiB     | protocol guard                         |
| Heartbeat interval/timeout| 15s / 45s  | from `WELCOME`                         |
| Resume grace window       | 30s        | subdomain held during this window      |

## 14. Full example flow (fresh tunnel)

```
client → HELLO      { protocol:1, token, tunnel:{} }
gateway→ WELCOME    { tunnelId, subdomain:"abc123", url }
gateway→ PING       (every 15s)  ;  client→ PONG
        ── public GET https://abc123.mylocalon.com/health ──
gateway→ HTTP_REQUEST  { reqId, method:"GET", path:"/health", bodyB64:"" }
client → HTTP_RESPONSE { reqId, status:200, bodyB64:"T0s=" }
        ── socket drops ──
gateway: ACTIVE → DISCONNECTED (30s grace, subdomain held)
client → HELLO      { protocol:1, token, resume:{ tunnelId, resumeToken } }
gateway→ WELCOME    { tunnelId, subdomain:"abc123"  (same) }
        ── user Ctrl-C ──
client → CLOSE      { tunnelId }
gateway: → CLOSED, subdomain released after grace
```

---

## 15. Versioning

- Breaking change → increment `protocol` (`2`) and subprotocol (`mylocalon.v2`).
  Gateways MAY support multiple versions concurrently during migration.
- Additive change → new optional fields or negotiated capabilities under the
  **same** `protocol` version. Receivers ignore unknown fields (§3), so old
  clients keep working.
